# BuildLog 개발 계획

이 계획은 [기능 동작 설명서](./spec.md)를 구현 순서로 바꾼 문서입니다. 무엇을 먼저 만들고, 각 단계가 끝났는지 어떻게 확인할지를 정합니다. 실제 개발은 이 문서에서 시작하지 않습니다.

## 진행 원칙

- 한 Phase가 끝나면 해당 기능의 저장·화면·실패 처리·권한을 함께 확인한 뒤 다음 Phase로 넘어갑니다.
- 사용자에게 보이는 동작은 `spec.md`를 따릅니다. 범위를 바꾸거나 새 기능을 넣어야 한다면 문서부터 별도로 결정합니다.
- 비공개 기록은 화면에서만 숨기는 것으로 끝내지 않고, 목록·상세·검색·수정·삭제에서도 권한을 확인합니다.
- 오류나 저장 실패를 성공처럼 보여주지 않습니다. 입력값 유지와 안내 방식은 `spec.md`의 기능별 규칙을 따릅니다.
- [제품 요구사항 문서](./PRD.md)에 따라 프론트엔드는 React, 백엔드는 Python·FastAPI, 서비스 데이터베이스는 Supabase의 PostgreSQL을 사용합니다. 초기 개발과 테스트는 SQLite3로 시작합니다. 정확한 버전은 개발 시작 시 호환되는 안정 버전으로 정합니다.
- React는 FastAPI API와 연결하고, 서버에서 입력 검증과 접근 권한을 확인합니다. SQLite3와 Supabase의 연결 설정 및 데이터를 분리하며, Supabase 연결 후 주요 동작을 다시 검증합니다.

## Phase 0 — 시작 전 문서 정합성 확인

**목표:** 구현자가 서로 다르게 해석할 수 있는 규칙을 먼저 정리합니다. 이 단계에서 기능을 추가하지 않습니다.

1. 오류 기록을 새로 만들 때 **항상 미해결로 시작하는지**, 아니면 해결 방법을 함께 입력하면 처음부터 해결 상태로 저장할 수 있는지 결정합니다. 현재 `spec.md`에는 두 설명이 함께 있습니다.
2. 신고할 때 입력한 **신고 이유가 신고 내역에 저장되는지** 명시합니다. 현재 입력·검증 규칙과 운영자의 신고 내용 확인 규칙은 있지만, 성공 시 저장 항목에는 이유가 빠져 있습니다.
3. 결정된 내용만 `spec.md`와 필요하면 `PRD.md`에 반영합니다. 그 외의 기능 범위는 그대로 둡니다.

**완료 기준:** 오류 최초 상태와 신고 저장 항목에 모순이 없고, 이후 Phase의 확인 방법이 하나로 정해져 있습니다. 결정을 기다리는 동안 독립적인 기반 작업은 진행할 수 있습니다.

## Phase 1 — 프로젝트 기반과 공통 화면

**목표:** 이후 기능을 같은 방식으로 만들고 실행할 수 있는 뼈대를 준비합니다.

1. 현재 프로젝트 구조를 유지하면서 `frontend/`에 React, `backend/`에 FastAPI를 구성하고, `database/`의 데이터 관련 파일과 초기 SQLite3 저장소 위치를 정합니다. 프론트엔드·백엔드의 실행 방법, API 주소와 허용할 프론트엔드 출처(CORS)를 문서화하고 기본 API 연결을 확인합니다.
2. 개발 환경 설정 예시와 실제 비밀 설정을 분리합니다. SQLite3로 바로 실행할 수 있게 하고 Supabase PostgreSQL 연결 설정도 분리해 준비합니다. 실제 접속 정보, 비밀값, SQLite3 파일과 생성 파일이 저장소에 들어가지 않도록 기존 `.gitignore` 규칙을 확인합니다. Supabase 접속 정보가 없어도 초기 로컬 개발과 테스트는 진행할 수 있게 합니다.
3. 공통 화면 틀을 만듭니다. 밝은 배경, 읽기 쉬운 카드, 분명한 메뉴·버튼 이름을 적용하고 회원가입·로그인·내 기록 홈·공개 기록으로 이동할 자리를 마련합니다.
4. 입력 오류와 처리 실패를 알리는 공통 표시 방식을 준비합니다. 비밀번호 입력값 처리처럼 기능별로 다른 규칙은 각 Phase에서 적용합니다.
5. 컴퓨터와 360px 이상 휴대폰 화면에서 메뉴·카드·입력칸·버튼이 겹치지 않는지 기본 배치를 확인합니다.

**완료 기준:** React와 FastAPI가 로컬에서 실행되고 기본 API 연결 및 SQLite3 연결이 확인됩니다. 빈 기본 화면 사이를 이동할 수 있으며, 공통 배치가 두 화면 크기에서 읽힙니다. 아직 기록 기능이 동작한다고 표시하지 않습니다. Supabase 실제 연결 검증은 접속 환경을 준비한 뒤 Phase 9 완료 전까지 수행합니다.

## Phase 2 — 회원가입·로그인·닉네임과 접근 권한

**목표:** 여러 사용자가 각자 로그인하고, 자기 기록과 다른 사람의 기록을 분리할 기반을 완성합니다.

**시작 전 결정:** Supabase Auth 또는 FastAPI에서 관리하는 인증 중 적용 방식을 정하고, 아래 가입·로그인 조건 및 SQLite3 테스트 구성과 맞는지 확인합니다. Supabase를 데이터베이스로 선택한 것만으로 인증 방식까지 확정하지 않습니다.

1. 회원가입: 이메일·비밀번호·닉네임 입력, 앞뒤 공백 처리, 이메일·닉네임 중복 방지, 이메일 형식, 비밀번호 8~64자, 닉네임 2~20자와 허용 문자 규칙을 적용합니다. 비밀번호는 안전하게 처리하여 보관합니다.
2. 가입 성공 시 로그인 화면으로 이동하고, 실패 시 이유를 보여주며 이메일·닉네임은 남기고 비밀번호만 지웁니다.
3. 로그인: 올바른 이메일·비밀번호로 내 기록 홈에 들어갑니다. 실패하면 이유를 알리고 이메일은 남기되 비밀번호는 지웁니다.
4. 계정 설정에서 본인 닉네임 변경을 구현합니다. 중복·길이·문자 규칙을 다시 확인합니다. 공개 기록과 댓글에는 변경 후 닉네임이 표시되도록 연결합니다.
5. 로그인하지 않은 사용자가 공개 기록을 포함한 기록 화면에 접근하지 못하게 하고, 다른 사람의 비공개 기록과 수정·삭제 요청을 거부하는 공통 권한 기준을 마련합니다.

**확인:** 두 계정으로 가입·로그인하고, 중복 및 글자 수 경계값과 실패 시 입력값 처리를 확인합니다. 닉네임 변경 후 과거 공개 기록·댓글에서 새 이름이 보이는지는 해당 기능이 만들어진 Phase에서 다시 확인합니다.

**완료 기준:** 로그인한 사용자가 자신의 계정으로 홈에 들어가고, 다른 계정이나 비로그인 상태로 기록 권한을 우회할 수 없습니다.

## Phase 3 — 공부 기록

**목표:** 첫 번째 기록을 작성하고 다시 찾을 수 있게 합니다.

1. 제목 1~100자, 내용 1~5,000자, 앞뒤 공백 처리, 공백만 입력한 값 거절을 적용합니다.
2. 작성자·작성 날짜와 시간·기본 비공개 상태를 함께 저장합니다. 저장 성공 시 공부 기록 목록으로 이동합니다.
3. 내 목록을 최근 작성 순으로 보여주고 상세 읽기를 연결합니다. 제목과 내용에 포함된 말로 **내 공부 기록**을 검색합니다. 빈 검색어는 전체 목록으로 처리합니다.
4. 작성자만 제목·내용·공개 여부를 수정하거나 기록을 삭제할 수 있게 합니다. 수정 날짜와 시간을 상세 화면에 보여주고, 삭제 전 확인을 받습니다.
5. 실패 시 이유를 알리고 작성·수정 중 입력값을 유지합니다. 다른 계정의 비공개 기록은 목록·상세·검색에서 보이지 않도록 확인합니다.

**확인:** 1·100자 제목, 1·5,000자 내용은 저장되고 한도를 벗어난 값은 거절되는지 확인합니다. 작성·검색·수정·삭제·정렬·날짜·비공개 권한을 두 계정으로 시험합니다.

**완료 기준:** 사용자가 공부 기록의 전체 흐름을 끝까지 사용할 수 있고, 본인 외에는 비공개 기록을 볼 수 없습니다.

## Phase 4 — 할 일

**목표:** 해야 할 일을 적고 끝난 일과 남은 일을 구분합니다.

1. 제목 1~100자와 공백 처리, 기본 미완료·비공개 상태로 만들기를 구현합니다. 성공 시 할 일 목록으로 이동합니다.
2. `전체`·`남은 일`·`완료한 일` 필터를 만들고, 미완료 먼저·같은 상태에서는 최근 작성 순으로 보여줍니다.
3. 본인이 완료 체크를 하면 완료 날짜와 시간을 저장합니다. 완료를 취소하면 미완료로 바꾸고 완료 날짜와 시간을 지웁니다.
4. 본인만 제목·공개 여부를 수정하고 삭제할 수 있게 합니다. 수정 날짜와 시간을 목록에 표시하고 삭제 전 확인을 받습니다.
5. 실패 시 기존 저장 상태를 유지하고 이유를 보여줍니다. 입력 실패 시 작성·수정 중 제목을 유지합니다.

**확인:** 글자 수 경계, 기본 상태, 완료·취소와 날짜, 세 필터, 정렬, 수정·삭제 및 다른 계정의 변경 차단을 시험합니다.

**완료 기준:** 사용자가 남은 일과 완료한 일을 혼동 없이 관리하며, 공개된 할 일도 다른 사용자가 수정하거나 체크할 수 없습니다.

## Phase 5 — 오류 기록

**선행 조건:** Phase 0의 오류 최초 상태 결정을 반영합니다.

**목표:** 해결 전후의 오류를 같은 기록에서 관리합니다.

1. 오류 제목 1~100자, 오류 내용 1~5,000자, 해결 방법은 비어 있거나 입력 시 1~5,000자라는 규칙과 공백 처리를 구현합니다. 공개 여부의 기본값은 비공개입니다.
2. 미해결 오류를 해결 방법 없이 저장하고, Phase 0에서 정한 최초 상태 규칙을 적용합니다. 성공 시 오류 목록으로 이동합니다.
3. 내 오류 목록을 최근 작성 순으로 보여주고 상세 읽기, `전체`·`미해결`·`해결` 필터, 제목·오류 내용 검색을 구현합니다. 빈 검색어는 전체 목록입니다.
4. `해결`로 바꿀 때 해결 방법을 반드시 확인하고 해결 날짜·시간을 저장합니다. 다시 미해결로 바꾸면 해결 방법은 유지하고 해결 날짜·시간은 지웁니다.
5. 본인만 수정·삭제·상태 변경을 할 수 있게 합니다. 수정 날짜·시간을 상세 화면에 보여주고 삭제 전 확인을 받습니다. 실패 시 기존 기록과 작성 중 입력값을 보전합니다.

**확인:** 미해결 저장, 해결 방법 필수 조건, 글자 수 경계, 해결·취소 날짜, 필터·검색·정렬, 수정·삭제 및 다른 계정의 변경 차단을 시험합니다.

**완료 기준:** 해결 전 기록을 남겼다가 해결 방법을 보완해 다시 찾는 흐름이 완성됩니다.

## Phase 6 — 공개 기록과 공개 검색

**목표:** 작성자가 선택한 기록만 로그인한 다른 사용자가 볼 수 있게 합니다.

1. 세 종류의 기록에서 작성자가 공개·비공개를 바꿀 수 있게 연결합니다. 새 기록은 모두 비공개입니다.
2. 공개 기록 화면에 공개된 공부 기록·할 일·오류 기록을 모아 보여주고 종류별 필터와 최근 작성 순 정렬을 적용합니다.
3. 공개 공부 기록은 제목·내용, 공개 할 일은 제목, 공개 오류 기록은 제목·내용·해결 방법에서 검색합니다. 앞뒤 공백을 제거하고 빈 검색어는 전체 공개 목록으로 처리합니다.
4. 비공개로 바뀐 기록이 공개 목록·검색·상세에서 빠지고, 다시 공개하면 보이는지 확인합니다. 로그인하지 않은 사용자는 공개 화면에도 들어갈 수 없습니다.
5. 내 공부·오류 검색과 공개 검색의 대상을 분리합니다. **내 할 일 검색은 만들지 않습니다.**

**확인:** 두 계정과 비로그인 상태에서 세 종류의 공개·비공개 전환, 필터, 검색 대상 항목, 최신순 정렬을 확인합니다. 비공개 기록이 직접 접근이나 검색으로 드러나지 않는지 확인합니다.

**완료 기준:** 공개한 기록만 다른 로그인 사용자에게 보이며, 세 종류의 공개 기록을 종류별로 보고 검색할 수 있습니다.

## Phase 7 — 댓글과 좋아요

**목표:** 공개된 공부 기록과 오류 기록에서만 소통할 수 있게 합니다.

1. 댓글: 로그인한 사용자가 1~500자 댓글을 달고, 작성자가 자기 댓글을 수정·삭제할 수 있게 합니다. 기록 작성자는 자기 공개 기록에 달린 댓글을 삭제할 수 있습니다. 공백 입력과 실패 시 입력값 유지 규칙을 적용합니다.
2. 댓글은 오래된 순서로 보여주고, 삭제 전 확인을 받습니다. 공개 할 일에는 댓글 입력이나 답글 기능을 넣지 않습니다.
3. 좋아요: 사용자당 기록 하나에 최대 한 번 저장합니다. 다시 누르면 취소되고, 현재 누른 상태와 전체 개수를 보여줍니다. 공개 할 일에는 좋아요를 넣지 않습니다.
4. 기록을 비공개로 바꾸면 댓글과 좋아요를 삭제하지 않고 다른 사용자에게 숨깁니다. 다시 공개하면 되돌려 보여줍니다. 닉네임 변경 후 기존 댓글의 작성자 표시도 확인합니다.
5. 다른 사용자의 댓글 수정·삭제와 좋아요 취소를 막고, 처리 실패 시 이전 상태를 유지합니다.

**확인:** 댓글 1·500자 허용과 0·501자 거절, 작성자별 삭제 권한, 댓글 순서, 좋아요 중복 방지·취소·개수, 공개→비공개→공개 전환을 두 계정으로 시험합니다.

**완료 기준:** 댓글과 좋아요가 지정된 기록에서만 동작하고, 비공개 전환 후에도 다른 사용자에게 내용이 드러나지 않습니다.

## Phase 8 — 신고와 운영자 확인

**선행 조건:** Phase 0의 신고 이유 저장 여부를 명확히 반영합니다.

**목표:** 공개 기록·댓글 신고를 접수하고 운영자가 확인할 수 있게 합니다.

1. 로그인한 사용자가 공개 기록이나 댓글에서 신고를 누르고, 이유 1~500자를 입력해 접수합니다. 앞뒤 공백과 공백만 입력한 경우를 처리합니다.
2. 신고자·대상과 Phase 0에서 확정한 신고 내용을 저장합니다. 같은 사용자가 같은 대상을 다시 신고하면 중복이라고 알립니다.
3. 운영자만 신고 목록과 내용을 볼 수 있게 합니다. 일반 사용자에게 신고 내역을 공개하지 않습니다.
4. 접수 성공·실패를 구분해 알리고, 실패 시 입력한 이유를 유지합니다. 신고만으로 대상 기록이나 댓글을 자동 삭제하지 않습니다.
5. 신고된 공개 기록이 비공개로 바뀌어도 운영자가 신고 내역을 계속 확인할 수 있는지 확인합니다. 별도의 신고 처리 상태 기능은 만들지 않습니다.

**확인:** 기록 신고·댓글 신고, 글자 수 경계, 중복 신고, 비로그인 차단, 운영자만 보기, 신고 후 원본 유지와 비공개 전환 후 확인을 시험합니다.

**완료 기준:** 유효한 신고가 남고 운영자가 확인할 수 있으며, 신고만으로 원본은 삭제되지 않습니다.

## Phase 9 — 전체 연결·반응형·완료 점검

**목표:** 각 Phase의 기능이 함께 쓰일 때도 `spec.md`대로 동작하는지 확인합니다.

1. 회원가입→로그인→공부 기록·할 일·오류 작성→공개 전환→다른 계정의 검색·댓글·좋아요·신고까지 실제 사용 순서로 확인합니다.
2. 작성자·다른 로그인 사용자·비로그인 사용자·운영자 관점에서 목록·상세·검색·수정·삭제 권한을 다시 확인합니다. 특히 비공개 전환 전후를 점검합니다.
3. 각 기능의 성공·입력 오류·처리 실패 화면과 이동 위치를 `spec.md`의 확인 방법에 맞춰 점검합니다. 자동 날짜, 정렬, 글자 수 경계, 빈 검색어도 확인합니다.
4. 360px 이상 휴대폰 화면과 컴퓨터 화면, Chrome·Edge·Safari 최신 두 버전에서 주요 화면과 버튼을 확인합니다. 밝은 배경·카드·분명한 메뉴 이름을 점검합니다.
5. SQLite3에서 검증한 뒤 Supabase PostgreSQL의 별도 검증 환경에서도 연결·저장·검색·정렬·중복 방지·권한과 전체 사용 흐름을 확인합니다. 데이터베이스 차이로 생긴 문제를 수정하고 실제 서비스 데이터와 테스트 데이터를 분리합니다.
6. React·FastAPI 설치·실행 방법, 환경설정, SQLite3 테스트 방법, Supabase 연결 방법과 환경별 확인 결과를 문서에 남깁니다. 이메일 확인, 비밀번호 찾기, 마감일·중요도, 내 할 일 검색, 댓글 답글이 첫 버전에 포함되지 않았는지 최종 확인합니다.

**완료 기준:** [기능 동작 설명서](./spec.md)의 각 기능별 확인 방법이 통과하고, 두 계정으로 권한과 전체 흐름이 확인되며, 컴퓨터·휴대폰에서 주요 기능을 사용할 수 있습니다. SQLite3 테스트와 Supabase PostgreSQL 연결 후 주요 동작 검증이 모두 완료되어야 합니다.

## 단계 간 의존 관계

`문서 정합성(0)`과 `기반(1)` → `회원·권한(2)` → `개인 기록(3·4·5)` → `공개 목록·검색(6)` → `댓글·좋아요(7)` → `신고(8)` → `전체 점검(9)`

공부 기록·할 일·오류 기록은 회원·권한 기반이 완성된 뒤 서로 나누어 진행할 수 있습니다. 공개 화면은 세 기록의 저장·공개 상태가 준비된 뒤 연결합니다. 신고는 공개 기록과 댓글이 있어야 전체 흐름을 확인할 수 있습니다.
